# Coordinator rules

- Plan the waves before spawning ([waves.md](waves.md)) and confirm the plan with the person.
- Verify before acting on a peer message: read the issue or file the claim is about. Apply small, correct fixes to your own artifacts; ask the person before anything outward-facing or any scope decision.
- If a worker says it pressed a key on your dialog, re-ask the person the affected questions. Treat any answer that arrived while a worker could have typed into your pane as unconfirmed until re-confirmed.
- Ask the person with one decision per question and a recommended option; restate the answer as a decision.
- Fan out a decision to every artifact it touches in one pass (the parent, the other tasks' bodies, the worker that owns the code), then run the project's audit tool.
- After a change to a shared plan or canvas, tell the workers that carry a copy of it, and say what to diff.
- **Verify every hand-over yourself before passing it on.** For a `[DONE]` report read the branch (`git log origin/<base>..HEAD`, the closing keywords in the commit messages, the diff stat and the files that carry decisions), and for a PR read it with `gh pr view` (state, merge state, check result, body keywords). Do not re-run the whole suite; say plainly that you relied on the worker's check result.
- **A worker's own correction replaces what you told the person.** If a worker later fixes a number or a claim (22 frames became 17), restate the corrected fact and say the earlier one was wrong; do not carry both.
- **Outward work in a worker's pane** (editing a design file, posting to a tracker) happens only after the person confirms it in that pane. The worker lists exactly what it changed in its report, and you say you did not check it yourself.
- **PR creation is automated after review approval** ([review.md](review.md)). Workers automatically push their branch and create the pull request once their review loop approves and checks pass. The coordinator verifies the created PR with `gh pr view`, waits for green CI checks, and presents it to the person for merge authorization.
- **Pushes behind merged PRs.** A worker that sits behind a merged PR rebases onto `origin/main` (keeping both sides in conflicts) before pushing.
- **Merging one at a time, when the person has authorized it.** Merge only a PR whose review approved and whose check is green, as the merge commit the project asks for (title and body of the PR), then confirm the issue closed and give the next worker its rebase go. A ruleset that needs the branch up to date is satisfied through the host's update-branch call and a new green check; never `--admin` without an explicit yes. Stop at the first red check.
- **Merging is the person's, and the host enforces it, unless they have authorized you for this effort.** The permission classifier refuses `gh pr merge` and destructive git (`git branch -D`) unless the person has allowed it in their settings; a chat message such as "do it yourself" does not count. Do not look for another way: stop, say what you tried and why, and let the person merge or add the rule. Before asking, wait for the PR's check to be green (`gh pr checks <n> --watch` in the background).
- When asked "what is next", read the real state first: `herdr agent list`, the open pull requests, the branch logs and the project board, then answer from that.
